# Wrap every command in a transaction via a Mediator pipeline behavior

Several UseCases handlers write to more than one aggregate in a single command (`CreateFamilyMemberHandler` adds a `FamilyMember` then a `Programme`; before an earlier efficiency fix, `LogWorkoutSessionHandler` added a `WorkoutSession` then updated each logged lift's `WorkWeight` in a loop). Each `IRepository<T>.AddAsync`/`UpdateAsync` call commits independently via its own `SaveChangesAsync`, so a failure partway through left the database in a state the handler never intended — a `FamilyMember` with no `Programme`, for instance (#6).

We add `IUnitOfWork` (`LiftAndShift.Core.Interfaces`) — `BeginTransactionAsync`/`CommitTransactionAsync`/`RollbackTransactionAsync` — implemented in Infrastructure over `AppDbContext.Database.BeginTransactionAsync()`, and a `TransactionBehavior<TCommand, TResponse> : IPipelineBehavior<TCommand, TResponse> where TCommand : ICommand<TResponse>` in Core that begins a transaction before every command, commits it if the handler's `Result` succeeds, and rolls back (rethrowing) otherwise. It's registered once in `MediatorConfig.cs`, so every current and future command gets this for free — no handler writes its own transaction-handling code, and a single-write handler pays only the (negligible, single-process SQLite) cost of a transaction it didn't strictly need.

This was chosen over the alternative floated in #6 (deferring `SaveChangesAsync` inside `EfRepository` itself and committing once per request via a behavior) because it needed no change to the existing repository behavior or handler code — every handler already does the right sequence of `AddAsync`/`UpdateAsync` calls; they just needed to share one transaction instead of one each.

**Known limitation:** `EventDispatchInterceptor` dispatches domain events on every `SavedChangesAsync` call, including ones inside a not-yet-committed transaction — a mid-transaction domain event fires even if a later write in the same command causes a rollback. No current aggregate raises domain events (only the pre-existing `Contributor` does, outside any multi-write handler), so this isn't live yet, but it's a real gap that needs addressing (likely deferring dispatch to transaction commit) before any handler both writes multiple aggregates and raises domain events.
